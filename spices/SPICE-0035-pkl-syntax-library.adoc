= pkl:syntax Standard Library Module

* Proposal: link:./SPICE-0035-pkl-syntax-library.adoc[SPICE-0035]
* Author: link:https://github.com/stackoverflow[Islon Scherer]
* Status: Accepted
* Implemented in: Pkl 0.33
* Category: Standard Library

== Introduction

This SPICE introduces `pkl:syntax`, a new standard library module for parsing Pkl source code into a syntax tree, inspecting and transforming that tree, and rendering it back to Pkl source code.
It enables Pkl programs to read, analyze, and rewrite Pkl code.
This can be used as the foundation for tools such as code generators, linters, and migration scripts that are themselves written in Pkl.

== Motivation

Pkl source code is only accessible to the Pkl evaluator and to a handful of JVM-based tools.
There is currently no way for a Pkl program to treat Pkl code as data.
The workarounds available today all have drawbacks:

* Reading a module with `read()` yields a plain string.
Manipulating it requires regular expressions or string splitting, which is fragile, and does not understand nesting, comments, string interpolation, or multi-line strings.
* `pkl:reflect` describes the _evaluated_ shape of a module (classes, properties, types), but not its source.
It cannot see comments, formatting, expressions, or anything that was erased by evaluation.
* The `pkl-parser` and `pkl-formatter` JVM libraries expose a syntax tree, but only to Java and Kotlin consumers.
Using them requires writing and distributing JVM code, which is a significant barrier for authors of Pkl tooling.

Programmatic edits of Pkl code are common: bumping a dependency version in a `PklProject`, adding an annotation to every class, renaming a property across a package, or migrating code between Pkl versions.
These tasks are best expressed in Pkl itself, using a lossless view of the source.

== Proposed Solution

Add a `pkl:syntax` module with three pieces:

* `Parser`, which parses a string or `Resource` as a module or as an expression.
* `Node`, a generic, untyped syntax tree node, with methods to search and to transform the tree.
* `FormattingRenderer`, which renders a `Node` back to Pkl source code using the canonical Pkl formatter.

The tree is _lossless_: it keeps comments, whitespace-significant tokens, and the verbatim text of tokens, so parsing and rendering a module does not discard information.

[source,pkl]
----
import "pkl:syntax"

local parser = new syntax.Parser {}
local renderer = new syntax.FormattingRenderer {}

local module = parser.parseModule(read("Person.pkl"))

// Replace every integer literal with `0`
local rewritten = module.replaceChildrenOfType("int_literal_expr", (n) -> (n) { text = "0" })

output {
  text = renderer.render(rewritten)
}
----

Nodes are Pkl objects, so a transformed tree is built with ordinary amending, and a tree can also be constructed from scratch.

This SPICE covers the generic API only.
A typed API, with one class per kind of syntax node, is mentioned under <<Future directions>>.

== Detailed design

=== `Parser`

[source,pkl]
----
/// Utilities to parse Pkl source code to a syntax tree.
class Parser {
  /// Parse the string or resource as a Pkl module, returning either a syntax node or
  /// throwing an error.
  external function parseModule(source: String | Resource): Node

  /// Parse the string or resource as a Pkl module, returning either a syntax node or null
  /// in case of an error.
  external function parseModuleOrNull(source: String | Resource): Node?

  /// Parse the string or resource as a Pkl expression, returning either a syntax node or
  /// throwing an error.
  external function parseExpression(source: String | Resource): Node

  /// Parse the string or resource as a Pkl expression, returning either a syntax node or null
  /// in case of an error.
  external function parseExpressionOrNull(source: String | Resource): Node?
}
----

Parsing a module yields a node of type `"module"`.
Parsing an expression yields the expression node itself.
Syntax errors, including lexer errors, cause the throwing variants to fail with an error that points at the offending location, and the `OrNull` variants to return `null`.

=== `FormattingRenderer`

[source,pkl]
----
/// Renders a [Node] back to Pkl source code, using the canonical Pkl formatter.
class FormattingRenderer {
  /// The grammar version to target.
  ///
  /// `"V1"` matches Pkl 0.25 - 0.29, `"V2"` matches Pkl 0.30+.
  grammarVersion: "V1" | "V2" = "V2"

  /// Render [node] as Pkl source code.
  external function render(node: Node): String
}
----

Rendering applies the same formatting rules as `pkl format`.
The renderer formats from the tree, not from the original text, so a rendered tree is canonically formatted regardless of how it was written or built.
Only the `text` of terminal nodes is used. So constructed non-terminal nodes don't need to fill `text`.

=== `Node`

[source,pkl]
----
/// A generic, untyped node in the Pkl syntax tree.
///
/// A node is either a *leaf*, carrying no [children], or a *branch*, whose content is its
/// [children]. Either way, [text] is the source code the node spans.
class Node {
  /// The kind of this node.
  type: NodeType

  /// The child nodes, in source order. Empty for leaf nodes.
  children: List<Node>(isTerminal.implies(isEmpty))

  /// The parent node, or [null] for the root and for nodes not attached to a tree.
  hidden parent: Node?

  /// The verbatim source text for this node.
  ///
  /// [FormattingRenderer] only renders this text if this is a [terminal][isTerminal] node.
  text: String?(isTerminal.implies(this != null))

  /// The source location of this node.
  span: Span?

  /// Tells if this is a terminal node; i.e. a node that spans a single token of the grammar.
  ///
  /// A terminal never has [children], but not every node without [children] is a terminal.
  fixed isTerminal: Boolean = type is TerminalNodeType

  // ... query and transformation methods, described below
}
----

Properties:

* `type` identifies the grammar construct the node represents, see <<Node types>>.
* `children` holds the node's children in source order.
Terminal nodes always have no children.
* `parent` is set for nodes produced by the parser, which makes upward navigation possible.
A node that was constructed in Pkl code, or inserted by a transformation, has no parent of its own until it is attached to a tree.
* `text` is the verbatim source text of a node.
It is required for terminal nodes, and optional otherwise.
* `span` is the location of the node in its source.
It is `null`, by default, for nodes that did not come from a parser.

==== Searching downward

In the following, _child_ means any node below the receiver, at any depth, and never the receiver itself.
Searches are depth-first in pre-order.

[source,pkl]
----
/// Fold [operator] over this node and its descendants, top-down in pre-order.
external function fold<Result>(initial: Result, operator: (Result, Node) -> Result): Result

/// Returns the first child matching [predicate]. Throws if no child matches.
external function findChild(predicate: (Node) -> Boolean): Node

/// Same as [findChild()] but returns [null] if no child matches [predicate].
external function findChildOrNull(predicate: (Node) -> Boolean): Node?

/// Returns every child matching [predicate], in depth-first pre-order.
/// A matching node is searched for further matches, so a match may contain another.
external function findChildren(predicate: (Node) -> Boolean): List<Node>

/// Returns the first child whose [type] is [type]. Throws if no child has this type.
external function findChildOfType(type: NodeType): Node

/// Same as [findChildOfType()] but returns [null] if no child has this type.
external function findChildOfTypeOrNull(type: NodeType): Node?

/// Returns every child whose [type] is [type], in depth-first pre-order.
external function findChildrenOfType(type: NodeType): List<Node>
----

==== Transforming

Transformations return a new node tree with the given transformation applied.
Parenting relations are preserved.

[source,pkl]
----
/// Returns this node with the first child matching [predicate] replaced by [replacer]'s result.
///
/// The child replaced is the one [findChild()] returns. If there is none, the tree is
/// returned unchanged.
/// The replacement is left as it is, so it is not searched for further matches.
external function replaceChild(predicate: (Node) -> Boolean, replacer: (Node) -> Node): Node

/// Returns this node with every child matching [predicate] replaced by [replacer]'s result.
///
/// The children replaced are those [findChildren()] returns, except that a replacement is left
/// as it is, so a match nested in another match is left to [replacer].
external function replaceChildren(predicate: (Node) -> Boolean, replacer: (Node) -> Node): Node

/// Returns this node with the first child whose [type] is [type] replaced by [replacer]'s result.
///
/// If there is no such child, the tree is returned unchanged.
external function replaceChildOfType(type: NodeType, replacer: (Node) -> Node): Node

/// Returns this node with every child whose [type] is [type] replaced by [replacer]'s result.
external function replaceChildrenOfType(type: NodeType, replacer: (Node) -> Node): Node
----

==== Searching upward

Upward searches follow `parent` and consider only ancestors, never the receiver.
They find nothing for nodes that have no parent.

[source,pkl]
----
/// Returns the nearest parent matching [predicate]. Throws if no parent matches.
external function findParent(predicate: (Node) -> Boolean): Node

/// Same as [findParent()] but returns [null] if no parent matches [predicate].
external function findParentOrNull(predicate: (Node) -> Boolean): Node?

/// Returns the nearest parent whose [type] is [type]. Throws if no parent has this type.
external function findParentOfType(type: NodeType): Node

/// Same as [findParentOfType()] but returns [null] if no parent has this type.
external function findParentOfTypeOrNull(type: NodeType): Node?

/// Returns every parent matching [predicate], nearest first.
external function findParents(predicate: (Node) -> Boolean): List<Node>

/// Tells whether any parent matches [predicate].
external function hasParent(predicate: (Node) -> Boolean): Boolean

/// Tells whether any parent's [type] is [type].
external function hasParentOfType(type: NodeType): Boolean
----

=== `Span` and `SourceLocation`

[source,pkl]
----
/// A range of source code, spanning [start] (inclusive) to [end] (exclusive).
class Span {
  start: SourceLocation
  end: SourceLocation

  /// The display URI of this span.
  ///
  /// Rendered for the editor configured in the Pkl settings file, the same way a location is
  /// rendered in a stack trace.
  displayUri: String
}

/// A position in source code, given as a 1-based line and column.
class SourceLocation {
  line: UInt
  column: UInt

  /// A URI identifying this source location, suitable for display.
  ///
  /// The exact format depends on where this location came from and on the editor configured in the
  /// Pkl settings file.
  displayUri: String
}
----

=== Node types

`NodeType` is a typealias of all possible node types.

[source,pkl]
----
/// The kinds of node in the Pkl syntax tree.
typealias NodeType =
  TerminalNodeType
    | ExprNodeType
    | TypeNodeType
    | ObjectMemberNodeType
    | ClassMemberNodeType
    | ModuleMemberNodeType
    // module structure, parts of members, parts of expressions, parts of types
    | "module"
    | "doc_comment"
    // ...
----

A node type may belong to more than one group. For example, `"int_literal_expr"` is both a terminal and an expression.
The remaining node types describe the module structure and the intermediate pieces of larger constructs, such as `"import"`, `"annotation"`, `"parameter_list"`, or `"if_condition"`.

Comments, doc comments, and shebang lines are retained as nodes in the tree.

NOTE: `NodeType` literals mirror the generic syntax tree of the Pkl parser.
They are named after the grammar and may gain new members as the Pkl grammar evolves.

== Compatibility

This is a purely additive change.
It adds a new standard library module and changes no existing module.

The node types are part of the module's public API.
Because they mirror the grammar, new language features can add node types, and code that exhaustively handles `NodeType` should expect that.

== Future directions

* A typed API.
Instead of a single generic `Node`, a `Module`, `Class`, `Property`, `IfExpr`, and so on could expose named, typed properties and construct trees without knowing the shape of `children`.
Such an API could be layered on top of the generic API, and is expected to be proposed separately.
* Further navigation helpers, such as siblings or ancestors-or-self, and a visitor-style API.
* Additional renderers, such as one that outputs an S-expression representation of a tree for debugging.

== Alternatives considered

=== `pkl.experimental.syntax`

The link:https://github.com/apple/pkl-pantry/tree/main/packages/pkl.experimental.syntax[`pkl.experimental.syntax`] package in the Pkl Pantry already lets Pkl programs build Pkl source code.
It offers a typed class per construct (`ModuleNode`, `ClassNode`, `TypeAliasNode`, `AnnotationNode`, and so on), each of which has a `render` function.

It falls short of what this proposal sets out to do:

* It has no parser.
Programs can generate new code, but cannot read existing code, so it cannot be used to analyze or rewrite a module.
* Its coverage is partial.
It models module and class declarations, types, and a subset of expressions, and each new language feature requires new hand-written classes and rendering logic.
* It renders with its own logic, which is separate from the canonical Pkl formatter, so output can differ from `pkl format`.
* It is slow.
It is implemented entirely in Pkl, so rendering and any traversal run through the interpreter.
In `pkl:syntax`, almost everything non-trivial is `external` and implemented in Java, including the parser, the formatter, and the tree searches and transformations.
* It lives outside the standard library, so it is versioned independently of the language and has to be added as a package dependency.

A parser backed by the real Pkl grammar, and a renderer backed by the real formatter, can only be provided by the runtime.
The typed API under <<Future directions>> targets the ergonomics that `pkl.experimental.syntax` provides, on top of that foundation.

=== Exposing the syntax tree via `pkl:reflect`

`pkl:reflect` reflects the evaluated program.
Source-level concerns such as comments, unevaluated expressions, and formatting are not part of that model, and extending it would blur its purpose.

=== A typed API only

A typed tree is more ergonomic for common tasks, but it is much larger, and every grammar change requires a matching API change.
The generic API is small, covers every construct, including ones added in the future, and works as the base on which a typed API can be built.

=== Not retaining comments and tokens

A tree like the one `pkl-parser` produces for the evaluator discards comments and exact token text.
That is sufficient to evaluate a program, but makes rewriting source code lossy, which defeats the purpose of tools that edit code.
